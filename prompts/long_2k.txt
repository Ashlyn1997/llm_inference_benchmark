Long Context Technical Brief: Serving Large Language Models Under KV Cache Pressure

Large language model serving is a systems problem as much as it is a model problem. A request that appears simple at the API boundary can require substantial coordination among tokenization, scheduling, memory management, kernel execution, and network transport. The prefill phase reads the prompt and constructs attention keys and values for every transformer layer. The decode phase then extends that state one token at a time. When a service receives many long prompts concurrently, the cached keys and values often become the dominant resource. A benchmark that only measures short prompts can hide this pressure, because the service has little persistent attention state to manage. This document describes the operational behavior that a long-context benchmark is intended to exercise.

An autoregressive transformer produces a representation for each input token at every layer. During inference, retaining all intermediate activations would be unnecessarily expensive, but the attention mechanism still needs the key and value tensors from prior positions. The server therefore stores a KV cache. For a model with many layers, many attention heads, a nontrivial head dimension, and a long sequence length, the total cache allocation is significant. The exact size depends on model architecture, data type, attention variant, and implementation details. It grows approximately with the number of active tokens, not merely with the number of requests. A request containing two thousand prompt tokens can reserve much more cache capacity than a request containing a short conversational question, even before it starts generating an answer.

vLLM was designed around the observation that this cache is a central scheduling resource. Its paged attention approach manages KV memory in blocks rather than requiring each sequence to occupy one large contiguous region. This can reduce external fragmentation and enables flexible admission of requests with different prompt lengths. The implementation still has finite capacity. If a serving instance has limited GPU memory, long prompts reduce the number of sequences that can be resident at the same time. A scheduler may queue later requests, preempt existing sequences, swap state, or reject work depending on its configuration and the pressure on its cache blocks. These behaviors directly influence first-token latency, end-to-end latency, throughput, and variability across requests.

The prefill phase is especially important for this workload. Before a server can return the first generated content token, it must tokenize the text, allocate or reserve cache blocks, execute the transformer over the prompt, and record the resulting keys and values. With a long prompt, this computation is larger than it is for a short prompt. If several requests begin at once, the service may batch their prefills to improve GPU utilization. Batching provides high arithmetic intensity, but it also creates a tradeoff: a request can wait for other work to form a batch, and a very large batch can consume memory or extend the time before any individual request receives its first token. TTFT is a useful indicator of this combined queueing, admission, and prefill cost.

Decode has a different shape. Once a request has been prefetched, each new token attends to the stored context and appends one more KV entry. The amount of work per output token can increase with context length because attention must consider prior positions, although optimized kernels and attention layouts change the practical scaling. At high concurrency, decode steps from many sequences are commonly scheduled together. This creates a continuous competition between requests that need prefill and requests that need more decode tokens. A useful benchmark keeps output length fixed while changing concurrency so that differences in scheduling and cache pressure are easier to attribute to the serving system rather than to an accidental change in generated work.

The prompt used for this experiment is deliberately a single shared text. Every request should receive identical input content, a fixed maximum generation length, and comparable sampling settings. This controls the main workload variables. It also allows the benchmark to focus on cache residency and batching behavior rather than on a random distribution of token counts. The text is technical but does not require the model to solve a difficult task. A concise response is sufficient. The objective is not answer quality evaluation; it is a stable, repeatable input that creates a meaningful prefill and KV cache footprint. Reusing the same prompt is therefore intentional, even though real traffic normally contains diverse documents.

The benchmark client records GPU samples independently for each concurrency level. This separation matters because an idle interval between experiments should not be averaged into an active run. For each run, the monitor starts after warmup and stops immediately after the measured benchmark completes. The resulting CSV can be filtered using benchmark start and finish timestamps stored in summary metadata. The initial summary focuses on one selected GPU index. In a multi-GPU deployment, a model may use several devices, but averaging samples from an idle GPU with samples from the active GPU would make the result misleading. Additional devices can be analyzed later by selecting a different index or by extending the reporting layer without changing the request workload.

TTFT is measured from the beginning of one HTTP request to the first nonempty generated content received from the stream. It therefore includes client-visible network delay, server-side queueing, prompt prefill, and initial decode scheduling. It does not use an empty stream event as a proxy for output. Some OpenAI-compatible services emit role metadata or other structural frames before content, and treating those frames as a token would understate user-visible latency. When no nonempty content arrives, TTFT is absent rather than estimated. This convention makes aggregate TTFT percentiles easier to interpret and avoids mixing protocol behavior with generation behavior.

TPOT complements TTFT by describing the time spent after the first output token. It is derived from total latency, TTFT, and the number of completion tokens. The first output token is covered by TTFT, so TPOT divides remaining decode time by completion tokens minus one. The metric is only defined when reliable usage reports more than one completion token and when the resulting decode interval is nonnegative. It should not be inferred from the gaps between server-sent event chunks. A server may buffer tokens, merge them, emit control frames, or split text in ways that do not preserve token timing. This benchmark intentionally avoids calling those chunk intervals inter-token latency.

Concurrency is the primary experimental variable. At a low value, each request may find abundant cache capacity and a nearly empty scheduler. At moderate concurrency, prefill batches can become more efficient and output token throughput may rise. At higher values, the combined prompt length can exhaust a configured KV cache budget, increase queueing delay, or trigger preemption. The outcome is not guaranteed to be monotonic. A larger concurrency can improve device utilization while worsening TTFT and tail latency. For that reason, each run should retain average, P50, P95, and P99 values for TTFT, TPOT, and total latency rather than relying on one headline number.

The suggested series of concurrency levels is 8, 16, 32, and 64. With sixty-four measured requests at each level, the client permits at most the configured number of simultaneous HTTP requests while preserving a finite workload. This arrangement shows both saturation effects and the behavior of later requests that wait behind earlier waves. The generated output limit is fixed at 256 tokens to keep decode work material while avoiding an experiment dominated exclusively by generation length. If the server uses sampling, a deterministic temperature setting is helpful for reproducibility. If output token counts vary despite the fixed maximum, the returned usage values should still be used for throughput and TPOT calculations.

When reading the results, examine the relationships among several metrics. If output token throughput rises from concurrency 8 to 16 while TTFT remains stable, the server may be using larger batches effectively. If throughput plateaus but memory used approaches the available capacity and P99 TTFT climbs sharply, KV cache pressure or queueing is a plausible explanation. If GPU utilization remains low while latency is high, investigate networking, CPU tokenization, request limits, or scheduler configuration. If power draw and temperature increase without throughput gains, the service may be spending more time on inefficient work or waiting for memory-related synchronization. These are hypotheses, not proofs, but the combined request and GPU data makes them testable.

This workload is intended as a baseline for future KV cache memory comparisons. One experiment might change a server's GPU memory utilization target, cache block size, cache data type, or offload policy while keeping the model, prompt, output limit, concurrency series, and client version constant. Another might compare two vLLM releases or two GPU generations. The important practice is to change one meaningful variable at a time and retain the raw request and GPU files for later inspection. Summary statistics make quick charts convenient, but tails, failures, and individual request records often reveal the actual reason for a performance shift.

For a reliable run, verify that the endpoint is reachable, the OpenAI-compatible model name is accepted, and the client can write its result directory. Confirm that nvidia-smi is available when GPU metrics are required; if it is absent, the benchmark still produces latency and throughput results, but GPU summary fields are empty. Use the same long prompt file from the repository on local machines, Kaggle notebooks, and remote clients. Keep the prompt file unchanged during a comparison series. This provides a reproducible long-context pressure workload that can expose the interaction among prefill batching, KV cache allocation, GPU memory usage, and streaming generation under concurrent vLLM serving.
